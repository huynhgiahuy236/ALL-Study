01

Vòng đời Widget

Callback, dữ liệu từ cha và lỗi gọi API nhiều lần

D1Trong tree 3 giai đoạn — 7 bước, initState, didChangeDependencies và didUpdateWidget nằm ở đâu và khác nhau thế nào?

Vị trí trong tree

VÒNG ĐỜI STATEFULWIDGET
├── Giai đoạn 1: Khởi tạo
│   ├── createState()
│   ├── initState()                 ← đang so sánh
│   └── didChangeDependencies()     ← đang so sánh
├── Giai đoạn 2: Hoạt động/cập nhật
│   ├── build()
│   └── didUpdateWidget(oldWidget)  ← đang so sánh
└── Giai đoạn 3: Kết thúc
    ├── deactivate()
    └── dispose()
  • initState(): chạy một lần khi State được tạo; khởi tạo controller, listener hoặc dữ liệu ban đầu.
  • didChangeDependencies(): chạy sau initState và chạy lại khi dependency đang theo dõi thay đổi.
  • didUpdateWidget(oldWidget): chạy khi cha truyền cấu hình mới cùng type/key nên State cũ được giữ.

Nhớ: ba hàm này chỉ là ba callback nằm trong tree đầy đủ, không phải toàn bộ vòng đời. setState không thuộc 7 bước; nó chỉ yêu cầu build chạy lại.

D2Widget nhận userId từ cha. Làm sao tải lần đầu và tải lại khi ID đổi?

Đáp án và giải thích

initState() {
  super.initState();
  loadUser(widget.userId);
}

didUpdateWidget(oldWidget) {
  super.didUpdateWidget(oldWidget);
  if (oldWidget.userId != widget.userId) {
    loadUser(widget.userId);
  }
}

initState tải lần đầu; didUpdateWidget chỉ tải lại khi ID thật sự thay đổi.

D3Log là initState → didChangeDependencies → build → build. Suy ra điều gì?

Đáp án và giải thích

State được tạo lần đầu nên ba callback đầu chạy. Sau đó setState, dependency hoặc Widget cha thay đổi làm build chạy thêm lần nữa. State không bị tạo lại nên initState không chạy lần hai.

D4Đặt loadUsers() trong build khiến API gọi liên tục. Tìm lỗi và sửa.

Lỗi — nguyên nhân — cách sửa

build có thể chạy nhiều lần; response đổi state lại kích hoạt build và request mới.

Tải lần đầu trong initState. Nếu request phụ thuộc dữ liệu cha, kiểm tra thay đổi trong didUpdateWidget.

02

MVC và MVVM

Luồng dữ liệu, state và trách nhiệm của từng lớp

D1Controller và ViewModel khác nhau như thế nào?

Đáp án và giải thích

Controller: nhận sự kiện từ View, xử lý và điều phối Model/View.

ViewModel: cung cấp state và hành động; View quan sát state để rebuild.

Cả hai đều giúp tách logic khỏi giao diện; MVVM nhấn mạnh binding/quan sát.

D2Mô tả luồng đăng nhập theo MVVM.

Đáp án và giải thích

  1. View gọi viewModel.login().
  2. ViewModel đặt loading = true.
  3. ViewModel gọi Service/Repository.
  4. Nhận kết quả rồi cập nhật user hoặc error.
  5. View quan sát state để hiện loading, lỗi hoặc chuyển màn hình.
D3Lớp có users, isLoading, loadUsers() và notifyListeners() đóng vai trò gì?

Đáp án và giải thích

Lớp đó đóng vai trò ViewModel: giữ state cho giao diện, thực hiện hành động tải dữ liệu và thông báo View rebuild.

D4ViewModel nhận BuildContext để gọi dialog và Navigator. Vấn đề gì?

Lỗi — nguyên nhân — cách sửa

ViewModel phụ thuộc trực tiếp Flutter UI nên khó kiểm thử và tái sử dụng.

ViewModel chỉ phát state/kết quả; View quan sát rồi dùng context để dialog hoặc điều hướng.

CRUD với RESTful API

PUT/PATCH, chuyển JSON và xử lý status

D1Phân biệt PUT và PATCH.

Đáp án và giải thích

  • PUT: thường gửi đầy đủ để cập nhật/thay thế toàn bộ tài nguyên.
  • PATCH: chỉ gửi các trường cần thay đổi.

Cách dùng cuối cùng phải theo tài liệu của API.

D2Lấy danh sách JSON và chuyển thành List<User>.

Đáp án và giải thích

final res = await http.get(Uri.parse(url));
if (res.statusCode == 200) {
  final data = jsonDecode(res.body) as List;
  return data.map((e) => User.fromJson(e)).toList();
}
throw Exception('Không tải được dữ liệu');
D3API trả 201, 204, 400, 404 và 500. Ứng dụng hiểu thế nào?

Đáp án và giải thích

  • 201: tạo thành công.
  • 204: thành công, không có body.
  • 400: request/dữ liệu sai.
  • 404: không tìm thấy.
  • 500: lỗi phía server.
D4POST trả 201 nhưng code chỉ chấp nhận 200 nên báo lỗi. Sửa sao?

Lỗi — nguyên nhân — cách sửa

Điều kiện status không đúng hợp đồng endpoint.

Kiểm tra status API quy định, ví dụ res.statusCode == 201. Không giả định mọi thành công đều là 200.

Stateless và Stateful

Nơi sở hữu state và phạm vi rebuild

D1Vì sao StatefulWidget bất biến nhưng giao diện vẫn đổi?

Đáp án và giải thích

StatefulWidget chỉ là cấu hình bất biến. Dữ liệu thay đổi nằm trong đối tượng State. setState yêu cầu gọi lại build để tạo cấu hình giao diện mới.

D2Form đăng nhập nên giữ những state nào?

Đáp án và giải thích

  • isPasswordVisible: ẩn/hiện mật khẩu.
  • isLoading: trạng thái chờ API.
  • errorMessage: lỗi cần hiển thị.
  • TextEditingController: tạo trong State và dispose đúng lúc.
D3Dữ liệu danh sách do Provider giữ nhưng màn hình có TextField. Toàn màn hình có bắt buộc Stateful không?

Đáp án và giải thích

Không. View có thể quan sát Provider; chỉ vùng cần controller, focus hoặc state cục bộ mới cần Stateful. Chọn theo nơi sở hữu state.

Lỗi — nguyên nhân — cách sửa

Mỗi lần build, biến cục bộ được tạo lại với giá trị 0.

Đặt count thành field trong lớp State và cập nhật bên trong setState.

05

BuildContext

Phạm vi tổ tiên và sử dụng sau await

D1Widget, Element và BuildContext liên quan thế nào?

Đáp án và giải thích

  • Widget: cấu hình bất biến.
  • Element: đối tượng được gắn trong cây và giữ quan hệ cha/con.
  • BuildContext: interface do Element triển khai, đại diện vị trí đó.
D2Cho ví dụ đọc Theme, Provider và Navigator bằng context.

Đáp án và giải thích

final color = Theme.of(context).colorScheme.primary;
final vm = context.watch<UserViewModel>();
Navigator.of(context).push(...);

Theme/watch có thể đăng ký phụ thuộc; Navigator.of tìm Navigator tổ tiên.

D3Provider đặt bên trong HomePage. Context của cha phía trên có đọc được không?

Đáp án và giải thích

Không. Context chỉ tìm lên tổ tiên. Cần dùng context nằm dưới Provider hoặc đưa Provider lên cao hơn.

D4Dùng context điều hướng sau await khi màn hình có thể đã đóng. Sửa sao?

Lỗi — nguyên nhân — cách sửa

Trong thời gian await, Widget có thể đã bị tháo khỏi cây.

Kiểm tra if (!context.mounted) return; rồi mới dùng Navigator, dialog hoặc ScaffoldMessenger.

Cây thư mục MVC/MVVM

Thêm Service và phân loại file đúng trách nhiệm

D1Model, View, Controller/ViewModel và Service làm gì?

Đáp án và giải thích

  • Model: cấu trúc/chuyển đổi dữ liệu.
  • View: hiển thị và nhận thao tác.
  • Controller/ViewModel: logic và state trình bày.
  • Service: HTTP hoặc nguồn dữ liệu ngoài.
D2Tổ chức chức năng quản lý user theo MVVM.

Đáp án và giải thích

lib/
├─ models/user.dart
├─ services/user_service.dart
├─ viewmodels/user_viewmodel.dart
├─ views/user_list_page.dart
└─ main.dart

Luồng: View → ViewModel → Service → API; response quay lại để ViewModel cập nhật state.

D3Phân loại user.dart, user_page.dart, user_service.dart và user_viewmodel.dart.

Đáp án và giải thích

user.dart → models; user_page.dart → views; user_service.dart → services; user_viewmodel.dart → viewmodels. Cần dựa vào trách nhiệm code, không chỉ tên file.

D4View gọi http.get còn Model gọi Navigator. Sai ở đâu?

Lỗi — nguyên nhân — cách sửa

View bị trộn giao tiếp dữ liệu; Model bị phụ thuộc giao diện.

Chuyển HTTP sang Service, logic sang Controller/ViewModel; View điều hướng theo kết quả.

07

Service CRUD

Đọc response và sửa lỗi gọi API phổ biến

D1Vì sao nên tách Service thay vì gọi HTTP trong View?

Đáp án và giải thích

  • Tách UI khỏi URL, header, JSON và status.
  • Dễ tái sử dụng, kiểm thử và thay package.
  • View tập trung hiển thị; ViewModel tập trung state.
D2Viết hàm PATCH cập nhật tên user.

Đáp án và giải thích

Future<User> updateName(int id, String name) async {
  final res = await http.patch(
    Uri.parse('$baseUrl/users/$id'),
    headers: {'Content-Type': 'application/json'},
    body: jsonEncode({'name': name}),
  );
  if (res.statusCode == 200) {
    return User.fromJson(jsonDecode(res.body));
  }
  throw Exception('Cập nhật thất bại');
}
D3GET trả 200 có JSON, DELETE trả 204 body rỗng. Xử lý khác nhau thế nào?

Đáp án và giải thích

GET kiểm tra 200 rồi jsonDecode body. DELETE nhận 204 chỉ cần xem là thành công; không parse body rỗng.

D4Service thiếu await, URL thiếu ID và luôn jsonDecode. Tìm ba lỗi.

Lỗi — nguyên nhân — cách sửa

  1. Thiếu await: đang xử lý Future → thêm await trong hàm async.
  2. Update/Delete thiếu ID → dùng $baseUrl/$id.
  3. Body có thể rỗng như 204 → kiểm tra status/body trước khi parse.
