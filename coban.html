01

Vòng đời Widget

Thứ tự và thời điểm các hàm được gọi.

D1Vòng đời StatefulWidget có mấy giai đoạn, mấy bước? Mỗi bước làm gì?

3 giai đoạn — 7 bước chính

VÒNG ĐỜI STATEFULWIDGET
│
├── Giai đoạn 1: Khởi tạo
│   ├── 1. createState()
│   ├── 2. initState()
│   └── 3. didChangeDependencies()
│
├── Giai đoạn 2: Hoạt động và cập nhật
│   ├── 4. build()
│   └── 5. didUpdateWidget(oldWidget)
│
└── Giai đoạn 3: Rời cây và kết thúc
    ├── 6. deactivate()
    └── 7. dispose()
  1. createState(): tạo đối tượng State cho StatefulWidget.
  2. initState(): khởi tạo dữ liệu, controller, listener; chạy một lần.
  3. didChangeDependencies(): chạy sau initState; có thể chạy lại khi Theme, Provider hoặc dependency khác thay đổi.
  4. build(): tạo giao diện; có thể chạy nhiều lần.
  5. didUpdateWidget(oldWidget): Widget cha truyền cấu hình mới nhưng State cũ vẫn được giữ.
  6. deactivate(): State tạm bị tháo khỏi cây và có thể được gắn lại.
  7. dispose(): State bị hủy vĩnh viễn; hủy controller, timer, stream và listener.

Điểm nhớ: đây là cách nhóm thành 3 giai đoạn để dễ học. setState() không thuộc 7 bước; nó chỉ yêu cầu build() chạy lại.

D2initState() và build() khác nhau thế nào?

Giải thích và ví dụ

  • initState() chạy một lần khi State được tạo. Dùng để gán giá trị ban đầu hoặc tạo controller.
  • build() trả về cây Widget để hiển thị. Nó chạy lần đầu và có thể chạy lại nhiều lần.
initState() → gán count = 0
build()     → hiển thị Text('$count')
setState()  → count đổi → build() chạy lại

Đáp án trọng tâm

setState() báo state đã đổi; Flutter gọi lại build(). initState() không chạy lại sau mỗi lần bấm.

D4Gọi controller.dispose() trong build(). Sai ở đâu?

Lỗi — lý do — cách sửa

Lỗi: build chạy nhiều lần nên controller bị hủy quá sớm.

Sửa: chuyển vào dispose(), sau đó gọi super.dispose().

02

MVC và MVVM

Tách dữ liệu, giao diện và logic.

D1MVC và MVVM gồm những thành phần nào? Mỗi thành phần làm gì?

Đáp án đầy đủ

MVC:

  • Model: chứa dữ liệu và quy tắc xử lý dữ liệu.
  • View: hiển thị giao diện và nhận thao tác người dùng.
  • Controller: nhận yêu cầu từ View, xử lý logic, làm việc với Model rồi yêu cầu cập nhật View.

MVVM:

  • Model: chứa dữ liệu.
  • View: hiển thị giao diện và gửi sự kiện.
  • ViewModel: giữ state và logic dành cho View.
  • Binding/quan sát: View lắng nghe ViewModel và tự cập nhật khi state đổi.

Khác nhau chính: MVC thường đi qua Controller; MVVM để View quan sát ViewModel. Đây là kiến trúc logic, không phải quy định cứng về thư mục.

D2Dùng chức năng tăng số để minh họa hai kiến trúc.

Luồng chạy cơ bản

MVC: người dùng bấm nút ở View → Controller nhận sự kiện → Controller tăng giá trị trong Model → View hiển thị giá trị mới.

MVVM: người dùng bấm nút ở View → gọi viewModel.increment() → ViewModel đổi state và thông báo → View đang lắng nghe rebuild.

Trong Flutter, một lớp dùng Provider, Riverpod hoặc BLoC có thể đóng vai trò gần ViewModel; các công cụ này không tự động đồng nghĩa với MVVM.

D3View dùng Consumer và đổi khi notifyListeners() chạy. Gần kiến trúc nào?

Đáp án trọng tâm

Gần MVVM: ChangeNotifier đóng vai trò ViewModel, còn Consumer quan sát dữ liệu để cập nhật View.

D4View vừa vẽ giao diện, vừa gọi API, vừa xử lý dữ liệu. Vấn đề gì?

Lỗi — lý do — cách sửa

Trộn nhiều trách nhiệm làm file khó đọc và khó kiểm thử.

Tách Model; đưa logic sang Controller/ViewModel; View chỉ hiển thị và chuyển sự kiện.

CRUD với RESTful API

HTTP method, JSON và status code.

D1CRUD ánh xạ với HTTP method như thế nào? Cần nhớ gì khi gọi API?

Đáp án đầy đủ

Create = POSTRead = GETUpdate = PUT/PATCHDelete = DELETE
  • GET: lấy một hoặc nhiều dữ liệu.
  • POST: tạo dữ liệu mới.
  • PUT: thường cập nhật toàn bộ đối tượng; PATCH: cập nhật một phần.
  • DELETE: xóa dữ liệu.
  • Flutter thường dùng package http hoặc dio.
  • jsonEncode()/toJson(): chuyển dữ liệu để gửi; jsonDecode()/fromJson(): chuyển response thành đối tượng Dart.

Status thường gặp: 200 thành công, 201 tạo thành công, 204 thành công không có body, 400 yêu cầu sai, 404 không tìm thấy, 500 lỗi server.

  • Thành công thường là 201 Created.

04

Stateless và Stateful

Chọn Widget theo trạng thái thay đổi.

D1Phân biệt StatelessWidget và StatefulWidget đầy đủ.

Đáp án đầy đủ

  • StatelessWidget: không có đối tượng State riêng; phù hợp khi Widget chỉ nhận dữ liệu và hiển thị, không tự giữ trạng thái thay đổi.
  • StatefulWidget: có lớp State riêng; dữ liệu thay đổi được đặt trong State và gọi setState() để cập nhật giao diện.
  • Cả hai đều có build() và đều có thể build nhiều lần. Stateless có thể build lại khi Widget cha rebuild.
  • StatefulWidget không mặc định chậm hơn; hiệu năng phụ thuộc phạm vi rebuild và cách tổ chức Widget.

Cách chọn: không giữ state → Stateless; có counter, form, loading, chọn/bỏ chọn hoặc ẩn/hiện → Stateful ở mức cơ bản.

D2Cho ví dụ phù hợp với mỗi loại.

Đáp án trọng tâm

Stateless: tiêu đề, icon, thẻ thông tin tĩnh.

Stateful: counter, form, checkbox, trạng thái loading.

D3Biến isPasswordVisible đổi khi bấm icon. Nên dùng loại nào?

Đáp án trọng tâm

Cách cơ bản là StatefulWidget: biến nằm trong State và gọi setState() khi thay đổi.

D4StatelessWidget khai báo count rồi gọi setState(). Sai vì sao?

Lỗi — lý do — cách sửa

StatelessWidget không có đối tượng State và không có setState().

Chuyển sang StatefulWidget, đặt count trong lớp State; hoặc dùng trình quản lý state.

BuildContext

Vị trí Widget trong cây Element.

D1BuildContext là gì, có vai trò nào và tìm kiếm theo hướng nào?

Đáp án đầy đủ

  • BuildContext là interface đại diện vị trí của Widget trong cây Element; đối tượng Element triển khai BuildContext.

1. GET danh sách

Future<Map<String, dynamic>>
    _getRootObject() async {
  final response = await http.get(
    Uri.parse(baseUrl),
  );

  if (response.statusCode != 200) {
    throw Exception('Load failed');
  }

  final data = jsonDecode(response.body) as List;
  return Map<String, dynamic>.from(data.first);
}

Future<List<User>> getAllUsers() async {
  final rootObject = await _getRootObject();
  final users = rootObject['users'] as List? ?? [];
  return users
      .map((item) => User.fromMap(item))
      .toList();
}

Project đọc collection account_user, lấy object đầu tiên rồi đọc mảng users lồng bên trong.

2. GET theo ID

Future<User?> getUserById(int id) async {
  final response = await http.get(
    Uri.parse('$baseUrl/$id'),
  );

  if (response.statusCode == 200) {
    return User.fromMap(jsonDecode(response.body));
  }

  if (response.statusCode == 404) return null;
  throw Exception('Load user failed');
}

3. POST tạo User

Future<User> createUser(User user) async {
  final response = await http.post(
    Uri.parse(baseUrl),
    headers: {'Content-Type': 'application/json'},
    body: jsonEncode(user.toMap()),
  );

  if (response.statusCode == 201) {
    return User.fromMap(jsonDecode(response.body));
  }

  throw Exception('Create failed');
}

4. PUT cập nhật toàn bộ

Future<User> updateUser(User user) async {
  final response = await http.put(
    Uri.parse('$baseUrl/${user.id}'),
    headers: {'Content-Type': 'application/json'},
    body: jsonEncode(user.toMap()),
  );

  if (response.statusCode == 200) {
    return User.fromMap(jsonDecode(response.body));
  }

  throw Exception('Update failed');
}

5. PATCH cập nhật một phần

Future<User> patchUser(
  int id,
  Map<String, dynamic> data,

  final response = await http.patch(
    Uri.parse('$baseUrl/$id'),
    headers: {'Content-Type': 'application/json'},

  if (response.statusCode == 200) {

Future<bool> deleteUser(int id) async {
  final response = await http.delete(
    Uri.parse('$baseUrl/$id'),
  );

  if (response.statusCode == 200 ||
      response.statusCode == 204) {

D4Các lỗi cơ bản nào dễ gặp trong Service CRUD và màn hình?

Lỗi — lý do — cách sửa

  • Sai URL: ghép thừa hoặc thiếu resource → kiểm tra baseUrl trước khi nối ID.
  • Quên await: nhận Future thay vì Response → dùng await trong hàm async.
  • Quên jsonEncode: body không đúng JSON → dùng jsonEncode(user.toMap()).
  • Parse sai kiểu: response List nhưng ép Map, hoặc ngược lại → kiểm tra JSON thực tế trước khi fromMap.
  • Sai status: POST thường trả 201, GET/PUT/PATCH thường trả 200, DELETE có thể trả 200 hoặc 204.
  • Decode body 204: body rỗng gây FormatException → không jsonDecode khi status là 204.
  • Dùng context sau async: màn hình có thể đã đóng → kiểm tra if (!mounted) return; trước khi hiện SnackBar hoặc setState.
  • Controller dialog: nên giải phóng TextEditingController khi không còn dùng trong cấu trúc phù hợp.

Quy trình nhớ: tạo URL → gửi request → kiểm tra statusCode → decode JSON nếu có → fromMap/toMap → cập nhật state → hiển thị kết quả.
