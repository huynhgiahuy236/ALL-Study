01

Vòng đời Widget

Key, async, subscription và State được giữ hay tạo lại

D1Phân tích State được giữ hay tạo mới khi Widget cha đổi dữ liệu, key hoặc runtimeType.

Đáp án và phân tích

  • Cùng runtimeType và key: Flutter cập nhật Widget, giữ State và gọi didUpdateWidget.
  • Khác key hoặc runtimeType: State cũ đi đến deactivate/dispose và State mới được tạo.
  • GlobalKey có thể giúp chuyển một subtree sang vị trí mới mà giữ State.
D2Widget nhận userId, gọi API và lắng nghe stream. Thiết kế vòng đời phù hợp.

Đáp án và phân tích

initState: đăng ký stream và tải ID đầu tiên. didUpdateWidget: nếu ID đổi thì hủy request/subscription phụ thuộc ID cũ và tải ID mới. dispose: hủy stream, controller và tài nguyên. Sau await phải kiểm tra mounted trước khi setState.

D3Log có deactivate nhưng không có dispose, sau đó build lại. Suy ra gì?

Đáp án và phân tích

State có thể chỉ tạm rời cây rồi được gắn lại, thường do subtree di chuyển bằng key. deactivate không đồng nghĩa bị hủy vĩnh viễn; chỉ dispose mới kết thúc State.

D4Request hoàn tất sau dispose rồi gọi setState. Sửa toàn diện thế nào?

Phân tích lỗi và cách sửa

Callback async còn sống lâu hơn Widget nên setState trên State đã unmounted.

Hủy request/subscription khi có thể; sau await kiểm tra if (!mounted) return;; dispose controller/listener và tránh giữ callback tham chiếu State.

02

MVC và MVVM

Dependency direction, kiểm thử và tách lớp

D1So sánh MVC và MVVM về luồng dữ liệu, coupling và kiểm thử.

Đáp án và phân tích

MVC dùng Controller điều phối sự kiện và Model/View; MVVM để View quan sát state của ViewModel. MVVM dễ kiểm thử khi ViewModel không phụ thuộc BuildContext. Cả hai đều kém nếu View, logic và HTTP vẫn trộn chung.

D2Thiết kế đăng nhập gồm View, ViewModel, Repository, Service và token storage.

Đáp án và phân tích

  1. View gửi thông tin cho ViewModel.
  2. ViewModel cập nhật loading và gọi Repository.
  3. Repository điều phối Service cùng token storage.
  4. Service gọi API và chuyển response.
  5. Repository trả kết quả domain.
  6. ViewModel phát success/error; View điều hướng.
D3Sơ đồ ViewModel → Repository → Service nhưng Service lại gọi ViewModel. Vấn đề gì?

Đáp án và phân tích

Đây là phụ thuộc vòng tròn. Tầng dữ liệu không được phụ thuộc ngược tầng trình bày. Service chỉ trả dữ liệu/lỗi; Repository và ViewModel xử lý ở tầng cao hơn.

D4ViewModel tự new http.Client, gọi Navigator và lưu token. Hãy tách lại.

Phân tích lỗi và cách sửa

ViewModel ôm HTTP, UI navigation và storage nên khó mock/test.

Inject Repository vào ViewModel; Repository nhận Service và TokenStorage; View xử lý Navigator dựa trên state.

03

CRUD với RESTful API

Idempotency, retry, xác thực và lỗi nghiệp vụ

D1Giải thích idempotency của GET, PUT, PATCH, DELETE và POST.

Đáp án và phân tích

GET, PUT và DELETE được thiết kế idempotent: gửi lặp cùng request có hiệu ứng cuối tương đương. POST thường không idempotent nên retry có thể tạo trùng. PATCH có thể idempotent hoặc không tùy phép cập nhật.

D2Thiết kế request CRUD có token, timeout và phân trang.

Đáp án và phân tích

Gắn Authorization header; dùng query page/limit; đặt timeout; phân biệt lỗi mạng với lỗi HTTP; chỉ retry thao tác an toàn; trả model phân trang gồm items, page và total.

D3API trả 401, 403, 409, 422 và 429. Xử lý thế nào?

Đáp án và phân tích

  • 401: token thiếu/hết hạn, có thể refresh hoặc đăng nhập lại.
  • 403: đã xác thực nhưng không có quyền.
  • 409: xung đột dữ liệu.
  • 422: dữ liệu đúng JSON nhưng sai nghiệp vụ/validation.
  • 429: quá nhiều request; chờ Retry-After.
D4Mạng chậm làm người dùng bấm POST hai lần và tạo hai bản ghi. Sửa sao?

Phân tích lỗi và cách sửa

POST không idempotent và nút vẫn hoạt động khi request đang chạy.

Khóa nút bằng loading, chống gửi lặp; nếu server hỗ trợ, gửi idempotency key duy nhất để cùng thao tác chỉ tạo một lần.

04

Stateless và Stateful

Phạm vi rebuild, controller và state dùng chung

D1Phân biệt local state, shared state và app state; đặt chúng ở đâu?

Đáp án và phân tích

  • Local state: chỉ một Widget dùng, đặt gần Widget.
  • Shared state: nhiều Widget/màn hình dùng, đưa lên common ancestor hoặc state manager.
  • App state: đăng nhập, theme, giỏ hàng; quản lý ở tầng đủ cao nhưng không nhất thiết global mọi thứ.
D2Tách form phức tạp để chỉ vùng cần thiết rebuild.

Đáp án và phân tích

Tách field, validation message, loading button thành Widget nhỏ; dùng selector/listener theo từng phần state; giữ controller đúng owner; tránh setState ở màn hình cha khi chỉ một field thay đổi.

D3Log cho thấy toàn trang build khi một checkbox đổi. Nguyên nhân có thể là gì?

Đáp án và phân tích

State đặt quá cao hoặc View đang watch toàn bộ ViewModel. Đưa state xuống gần checkbox hoặc dùng Selector/select để chỉ lắng nghe giá trị cần thiết.

D4Tạo TextEditingController trong build gây lỗi gì và sửa sao?

Phân tích lỗi và cách sửa

Mỗi build tạo controller mới, mất selection/text và controller cũ không được dispose gây rò rỉ.

Tạo controller trong State/initState, cập nhật khi dữ liệu đầu vào đổi và dispose một lần.

05

BuildContext

InheritedWidget, nhiều Navigator và async gap

D1Vì sao context.watch làm rebuild còn context.read thường không?

Đáp án và phân tích

watch đăng ký Element hiện tại là dependency của InheritedWidget/Provider; khi giá trị thông báo đổi, Element được đánh dấu rebuild. read chỉ lấy giá trị tại thời điểm gọi, không đăng ký lắng nghe.

D2Ứng dụng có Navigator gốc và Navigator trong tab. Chọn context thế nào?

Đáp án và phân tích

Navigator.of(context) lấy Navigator gần nhất. Muốn đẩy route trong tab dùng context dưới Navigator tab; muốn dialog/route toàn ứng dụng có thể dùng rootNavigator hoặc context thuộc Navigator gốc.

D3Hai Provider cùng kiểu được lồng nhau. context đọc instance nào?

Đáp án và phân tích

Context lấy Provider tổ tiên gần nhất. Widget dưới Provider trong sẽ nhận instance trong; Widget nằm ngoài phạm vi đó nhận instance ngoài.

D4Dialog dùng context của root Navigator nhưng cần Provider chỉ có trong route con. Sửa sao?

Phân tích lỗi và cách sửa

Context của dialog nằm ngoài phạm vi Provider route nên không đọc được.

Truyền dữ liệu/ViewModel cần thiết vào dialog, đặt Provider cao hơn, hoặc cung cấp lại đúng instance cho subtree dialog.

06

Cây thư mục và kiến trúc

Feature-first, presentation/domain/data và dependency

D1So sánh tổ chức layer-first và feature-first.

Đáp án và phân tích

Layer-first gom toàn bộ models/views/services theo loại, dễ bắt đầu nhưng feature lớn bị phân tán. Feature-first gom auth/users/products riêng, dễ mở rộng theo chức năng; bên trong mỗi feature vẫn có thể chia presentation/domain/data.

D2Vẽ cấu trúc feature users theo ba tầng.

Đáp án và phân tích

features/users/
├─ presentation/
│  ├─ pages/
│  └─ user_viewmodel.dart
├─ domain/
│  ├─ user.dart
│  └─ user_repository.dart
└─ data/
   ├─ user_api_service.dart
   └─ user_repository_impl.dart

Dependency hướng vào domain; domain không import Flutter hoặc HTTP.

D3Repository interface ở domain nhưng implementation ở data. Vì sao?

Đáp án và phân tích

Domain định nghĩa nhu cầu dữ liệu mà không biết nguồn cụ thể. Data triển khai bằng API/database. ViewModel phụ thuộc abstraction nên có thể thay implementation và mock khi test.

D4Domain Model import package http, Repository gọi Navigator. Sai dependency nào?

Phân tích lỗi và cách sửa

Domain phụ thuộc hạ tầng HTTP; Repository dữ liệu phụ thuộc UI.

Đưa HTTP/DTO vào data; mapping sang entity domain; navigation thuộc presentation/View.

07

Service CRUD nâng cao

API client, exception mapping và request cạnh tranh

D1Phân biệt API Client, Service, Repository và ViewModel.

Đáp án và phân tích

  • API Client: base URL, header, timeout, gửi request chung.
  • Service: endpoint cụ thể và DTO.
  • Repository: nguồn dữ liệu, cache và mapping sang domain.
  • ViewModel: state và hành động cho View.
D2Thiết kế lỗi có kiểu thay vì throw Exception chung.

Đáp án và phân tích

API Client bắt timeout/network; Service ánh xạ HTTP thành Unauthorized, Validation, NotFound hoặc ServerFailure; Repository chuyển sang failure domain; ViewModel đổi failure thành thông báo phù hợp.

D3Hai request tìm kiếm trả về ngược thứ tự. Kết quả nào nên hiển thị?

Đáp án và phân tích

Chỉ kết quả của từ khóa mới nhất. Có thể hủy request cũ, dùng requestId tăng dần hoặc kiểm tra query hiện tại trước khi cập nhật state.

D4Refresh token bị lặp vô hạn khi endpoint refresh cũng trả 401. Sửa sao?

Phân tích lỗi và cách sửa

Interceptor áp dụng refresh cho cả request refresh hoặc retry không giới hạn.

Loại endpoint refresh khỏi interceptor; chỉ retry một lần; đồng bộ một refresh cho nhiều request; thất bại thì xóa phiên và yêu cầu đăng nhập lại.
